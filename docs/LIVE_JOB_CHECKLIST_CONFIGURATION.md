# Configuration fixes on existing job tasks

A task continues to use its selected job version (including that version's dirty
working copy). On each checklist reload, `JobChecklist` applies that definition's
label and handler configuration to matching unfinished stored items. This also
covers static templates and scoped items generated by decisions. Serialized
HTML tempstore checklists refresh their definitions after restoration while
retaining their working items.

For example, a task pinned to version 6 has a saved decision item. Adding a choice
to version 6's dirty configuration makes that choice available on the existing
item when the task reloads. Publishing version 7 does not move this task to 7.
Discarding the dirty copy makes unfinished work use the clean version 6 again.
The job editor's unsaved tempstore draft is not a runtime configuration source.

This is configuration resolution, not task recreation or a database migration:

- Item IDs and UUIDs, status, outcomes, working state and attempt history remain.
- Failed items receive configuration fixes and retain their state for retry.
- Completed items keep their recorded label and handler configuration, including
  finalized placeholders and the definitions used for their outcomes.
- A removed item retains its stored configuration. Existing branch activation
  rules still govern generated items whose definitions have disappeared.
- Reads do not save items. A subsequent item save records its current resolved
  configuration through the ordinary persistence path.

Changing a handler's plugin ID while an item has working state raises an explicit
configuration error. Restore that handler or use a new item name; do not feed
one plugin's private state to another. Changes within the same handler must keep
its working state and outcome definitions compatible. This does not introduce
plugin-code versioning or migrate active Flexiform/template execution snapshots.
Use a new job version or item name for incompatible workflow changes.

The shared execution preparer uses the checklist's resolved item after checking
its stored identity and host access. UI, API and workers therefore use the same
configuration; an input change during a running iteration remains covered by the
existing execution-input comparison before committing results.

Non-job checklist types keep their existing stored-configuration behaviour.
There is no new schema or update hook.

## Verification

`VersionedJobChecklistTest` covers persisted pending decisions receiving dirty
fixes, worker loading, stable identity, completed configuration and outcomes,
retained failed state, tempstore-style serialization, dirty-copy removal and
incompatible handler rejection.
`DecisionChecklistTemplatesTest` covers persisted generated item refresh, in
addition to branch activation, scoped contexts, nesting and processing.
